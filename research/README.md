# research: tsuri-navi 技術調査

## 1. プラットフォーム選定

### 選択肢A: PWA（Next.js / React）
**メリット:**
- App Store審査不要、URLを開くだけで使える
- ホーム画面追加でアプリっぽいUX
- iOS 16.4以降でプッシュ通知対応（ホーム画面に追加した場合のみ）
- 開発コスト低い、1つのコードベースで済む
- サブ機サーバーにデプロイすれば完全自前運用可能

**デメリット:**
- iOSのプッシュ通知はホーム画面追加が前提条件
- Background Syncは非対応（バックグラウンドでデータ更新できない）
- ストレージ制限がネイティブより厳しい

### 選択肢B: Swift（ネイティブiOS）
**メリット:**
- プッシュ通知が確実・リッチ（画像付き、サイレント通知も可）
- バックグラウンド処理が可能
- UXが最も良い

**デメリット:**
- Macが必須（Xcode）
- 無料Apple IDだと証明書が7日で失効 → 毎週再ビルドが必要
- Apple Developer Program（$99/年）払えば年単位で維持可能
- APIリクエスト自体は問題なくできる（URLSession）
- 個人用ならXcodeから直接インストールで十分

### 結論案: **PWA推奨**
- 「まず動くものを作る」にはPWAが圧倒的に速い
- プッシュ通知もiOS 16.4+で対応済み
- サブ機サーバーでバックエンド（定期バッチ・通知送信）を動かせば弱点を補える
- 後からSwiftネイティブに移行する余地も残せる

## 2. API選定

### 2a. 天気 + 海況（風・波）

#### ★ Open-Meteo（推奨）
- **完全無料**、APIキー不要、登録不要
- 非商用利用はCC BY 4.0ライセンス
- Weather API: 気温、風速・風向、降水量、気圧、湿度、天気コード
- Marine API: 波高、波の周期・方向、うねり
- 7日間予報、15分間隔データも可（日本はICONモデル）
- 1日10,000リクエストまで無料
- MCP Serverも存在（AIエージェント連携に便利）
- エンドポイント例:
    - 天気: `https://api.open-meteo.com/v1/forecast?latitude=37.05&longitude=140.89&hourly=temperature_2m,windspeed_10m,winddirection_10m,precipitation,pressure_msl,weathercode`
    - 海況: `https://marine-api.open-meteo.com/v1/marine?latitude=37.05&longitude=140.89&hourly=wave_height,wave_period,wave_direction,swell_wave_height`

#### Storm Glass
- 無料枠: 10リクエスト/日（商用不可）
- 天気 + 海況 + 潮汐をワンストップ
- 有料: €19/月〜
- 個人利用には無料枠が少なすぎる（1日10回だと複数ポイント×7日分すら取れない）

→ **Open-Meteoで天気・海況は十分。無料・無制限に近い。**

### 2b. 潮汐

#### ★ tide736.net（推奨）
- 日本沿岸736港の潮汐データ
- エンドポイント: `https://api.tide736.net/get_tide.php`
- POST/GETでリクエスト
- JSON形式でレスポンス
- 無料（アクセス数制限あり）
- サポートなし、予告なく終了の可能性
- **日本の港名・コードで指定できるので、日本の釣り場に最適**

#### TideCheck
- 日本705地点、無料50req/日
- バックアップとして有用

#### バックアップ案: 自前計算
- 海上保安庁の調和定数表（書誌742号）から潮汐推算は数学的に可能
- tide736.netが使えなくなった場合のフォールバック
- npmパッケージ等でtide計算ライブラリも存在

→ **tide736.netをメイン、TideCheckをバックアップ。将来的には自前計算も視野。**

### 2c. 距離・ルート計算

#### Google Maps Directions API
- 車での所要時間計算
- 料金: $5/1000リクエスト（月$200分の無料枠あり）
- 正確な車ルート・所要時間

#### OSRM (Open Source Routing Machine)
- 完全無料・セルフホスト可能
- 公開デモサーバーもあり（制限付き）
- サブ機サーバーにOSRMを建てれば無料で無制限
- 精度はGoogle Mapsに若干劣るが十分実用的

→ **まずはGoogle Maps（無料枠内）、コスト気になればOSRMに切り替え**

### 2d. 魚種×季節×餌の提案

#### 公開APIは存在しない
#### 選択肢:
1. **静的データベース（JSON/DB）** — 地域×月×魚種×釣り方×餌をマッピング
    - メリット: 高速、オフライン対応、APIコストゼロ
    - デメリット: データ作成に手間、更新が手動
2. **Claude API** — プロンプトで動的生成
    - メリット: 柔軟、地域差も対応、餌の提案も自然
    - デメリット: APIコスト、レスポンス遅延
3. **ハイブリッド（推奨）** — 基本データは静的DB、AIで補足・詳細提案
    - 基本の魚種×季節テーブルは静的に持つ
    - 「今日の条件ならこう釣れ」みたいな提案はClaude APIで生成
    - 生成結果をキャッシュして再利用

→ **ハイブリッド推奨。基本データは静的DB + 詳細提案にClaude API。**

## 3. 釣りやすさスコアのロジック案

### スコア要素と重み（100点満点）
| 要素 | 配点 | 良い条件 | 悪い条件 |
|------|------|----------|----------|
| 潮回り | 20点 | 大潮・中潮 | 若潮・長潮 |
| 潮の動き（時間帯） | 15点 | 満潮・干潮の前後1-2時間 | 潮止まり |
| 天気 | 15点 | 曇り・小雨 | 大雨・雷 |
| 風速 | 15点 | 微風(2-5m/s) | 強風(10m/s+) |
| 波高 | 15点 | 0.5-1.5m | 2.5m+ |
| 時間帯（朝夕マズメ） | 10点 | 日の出前後・日没前後 | 真昼間 |
| 気圧変化 | 5点 | 高気圧安定 | 急激な気圧低下 |
| 月齢 | 5点 | 新月・満月付近 | 半月 |

### 判定基準
- 80-100点: ◎ 絶好の釣り日和
- 60-79点: ○ まずまず良い
- 40-59点: △ 条件はいまいち
- 0-39点: × 行かないほうがいい

### 時間帯スコア
- 1時間ごとにスコアを算出
- 「今日のベストタイム」をハイライト表示

## 4. アーキテクチャ案

```
[iPhone (PWA)]
    ↕ HTTPS
[サブ機サーバー (Node.js / Next.js)]
    ├── API Gateway (天気・潮汐・ルートのプロキシ＆キャッシュ)
    ├── スコア計算エンジン
    ├── 定期バッチ（毎朝天気・潮汐データ取得→スコア計算）
    ├── プッシュ通知送信（Web Push / APNs）
    ├── Claude API（魚種提案）
    └── DB（SQLite or PostgreSQL）
         ├── 釣り場マスタ（緯度経度、名称、タイプ）
         ├── 魚種×季節マスタ
         ├── 天気・潮汐キャッシュ
         └── ユーザー設定（お気に入りポイント、通知設定）
```

### なぜサブ機サーバーが有効か
- 外部APIへのリクエストをサーバー側で集約＆キャッシュ → APIリミット節約
- 定期バッチで毎朝スコアを事前計算 → クライアントは結果を取るだけ
- プッシュ通知の送信元になる
- Claude APIキーをサーバー側に安全に保管

## 5. 技術スタック案

### フロントエンド
- **Next.js 14+**（App Router）
- React + TypeScript
- Tailwind CSS
- PWA対応（next-pwa）
- チャートライブラリ: Recharts or Chart.js（タイドグラフ用）
- 地図: Leaflet + OpenStreetMap（無料）or Google Maps

- Node.js
- SQLite（軽量、サブ機に最適）or PostgreSQL
- node-cron（定期バッチ）
- web-push（プッシュ通知）

### 外部API
- Open-Meteo（天気・海況）— 無料
- tide736.net（潮汐）— 無料
- Google Maps Directions（距離計算）— 無料枠内
- Claude API（魚種提案）— 従量課金

## 7. リスクと注意点
- tide736.netが突然終了する可能性 → バックアップ手段を用意
- Open-Meteoの日本沿岸データ精度 → 実データで検証必要
- サブ機サーバーの安定性（停電、ネットワーク）→ クラウド移行も視野
- 釣りやすさスコアの精度 → 実際の釣果でチューニングが必要
